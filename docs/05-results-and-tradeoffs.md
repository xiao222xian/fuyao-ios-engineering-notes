# 已有结果、失败尝试与取舍

## 源码能支持的结果

归档中可观察到原生查询、推荐相关展示与选择、生涯规划对话、历史记录和报告入口等模块。对部分具体问题，现存代码与历史记录可以互相印证：搜索使用在途状态和待刷新标记；选择覆盖状态包含组的作用域；报告逻辑区分生成状态与文档可用性。

这些是实现层面的结果，不能直接换算为用户满意度、录取成功率或稳定性指标。没有公开的对照实验或代表性统计样本，因此本文不提供量化收益表。

## 失败尝试与修正

| 原先的做法或问题 | 为什么不够 | 后续方向 | 保留的限制 |
|---|---|---|---|
| 用局部编号覆盖整页选择状态 | 不同组可能出现身份碰撞 | 使用院校、组、专业构成的作用域身份 | 缺失稳定标识时的回退仍需约束 |
| 用组级已选状态驱动所有子项 | 汇总状态与个体选择不是同一事实 | 子项独立判断，组级仅作聚合 | 批量动作影响范围仍要测试 |
| 每次添加/取消后刷新全部列表 | 用户感到卡顿、页面闪动和定位丢失 | 局部乐观更新并失败回滚 | 操作并发与回滚顺序并未全面证明 |
| 多个入口各自触发搜索 | 防抖不能覆盖所有触发源 | 在途合并与待刷新标记 | 严格最新上下文展示需要进一步设计 |
| 首屏数组为空就显示空态 | 请求未完成被误解为没有结果 | 增加已加载状态 | 多模式切换仍需回归 |
| 只比较 UI 和返回字段 | 环境和条件不同会先造成数据差异 | 先核对完整请求上下文 | 不能替代服务端数据治理 |
| 把生成完成当作文档完成 | 后台文件同步可能滞后 | 区分报告状态与文档入口 | 延迟、重试和恢复策略仍有限 |

上表是根据记录重新归纳的工程问题，不附内部工单、原始日志或合作方讨论。

## 兼容与统一之间

客户端兼容多种历史字段形态，可以减少一次接口变化造成的崩溃，但会增加解释成本。字段有对象和字符串两种形式、编号存在多个回退来源时，开发者必须清楚哪一层负责兼容，以及什么时候可以移除旧逻辑。

短期做兼容有合理性；长期更适合通过明确的数据契约和版本演进减少兼容分支。把所有不一致都留给客户端修补，会使每个新页面重复支付成本。

## 复用与复杂度之间

复用推荐卡片可以统一标签、历史信息、按钮和选择语义。但把所有页面差异都装进一个巨大组件，也可能引入难以理解的参数组合。更好的方向是共享稳定的数据解释与展示单元，在页面层明确入口特有行为。

生涯规划界面和状态管理仍有集中在大文件中的情况。项目结束时保留实际状态，而不是为了复盘好看，描述成已经完成全面模块化。

## 体验与真实状态之间

保留旧列表能减轻刷新失败的打断，乐观选择能缩短视觉反馈等待。但两者都可能暂时偏离服务器当前事实。用户需要知道哪些内容是缓存、哪些操作待确认，以及失败后如何恢复。

改进体验不应以隐藏失败为代价。下一轮迭代可考虑局部提示、操作版本和重新同步入口，而不是简单恢复到“失败就覆盖整个页面”。

## 上传与验收之间

历史记录中出现过 SDK 校验阻塞、构建目录锁和平台账号权限问题。它们分别属于依赖环境、构建运行与发布权限，不能统一解释为业务逻辑错误。

同样，生成构建产物、提交代码、上传附件和正式发布是不同动作。复盘应保留这些边界，避免把某一次成功操作扩张成整个系统交付完成的结论。

## 最值得保留的经验

用可解释的状态和不变量组织工程，比围绕页面数量总结工作更有价值。组合身份解释为什么按钮串状态，数据上下文解释为什么两端结果不同，独立的报告文件状态解释为什么“已生成”仍不能下载。它们既能指导实现，也能决定下一步应该验证什么。
