## 1. 数据建模与上下文归一化

平台将院校、专业、历史录取、招生计划、位次表和招生政策分别建模，再通过业务标识与地区、年份、批次和科目条件连接。成绩档案、候选预测、专业组、志愿条目、会话和报告文件属于不同实体。

关键是把“数据属于什么招生上下文”与“页面展示什么对象”分开。批次名称在档案表、候选表和组级数据中可能存在不同表达；查询入口先进行规范化，再展开到对应数据源可接受的名称。选科条件同样转换为候选筛选约束，而不是仅作为页面标签。

历史数据与当前招生计划各自保留字段来源，避免把一个列表的筛选项错误地用于另一个列表。客户端解码对可选字段和兼容形态作处理，但不将缺失的风险参考值直接解释成零。

## 2. 推荐引擎的执行流程

![推荐流程 / Recommendation pipeline](../assets/recommendation-pipeline.png)

### 条件构造

从档案取得地区、批次、分数、位次和科目，加载用户偏好，再构造院校属性、地区与专业的包含/排除条件。分数区间与位次区间分别处理：当适用的一分一段换算不能提供有效位次区间时，对应路径可以直接使用分数字段过滤。

### 两阶段查询

第一阶段读取足以筛选、比较和分页的轻量候选；第二阶段只为当前页加载完整院校、专业和历史信息。组级数据可以先按学校属性预筛，再与匹配的子项关联，避免先装载全部详情再裁剪。

这是一种减少数据装载范围的查询组织方式。实际耗时仍依赖数据规模、索引、筛选条件与运行环境，性能结论以受控基准测试和线上观测为依据。

### 风险参考映射

主推荐路径中的参考值以区间边界和中心锚点进行分段映射，再用于分层和排序。下面是便于说明的通用形式，不公开生产锚点、阈值或系数：

对相邻锚点 (x₀, y₀)、(x₁, y₁)，区间内的映射可以写成：

`f(x) = y₀ + (y₁ - y₀) × (x - x₀) / (x₁ - x₀)`

区间外按边界约束处理，不同区段连接成整体参考函数。这个公式解释映射机制，不表示相关数值已经通过真实录取样本进行概率校准。

### 专业组聚合与方案组织

先识别匹配子项，再按院校与专业组身份聚合。一个组包含匹配子项即可成为可展示候选，不应因为额外的重复组级范围过滤而意外丢失。候选去重、代表专业选择与风险分层随后参与展示。

志愿表与推荐列表有不同排序职责：推荐侧组织候选，志愿表保留用户编辑顺序。系统也包含按目标风险比例组织志愿、查看统计和导出结果的工具。

以下伪代码概括推荐流程中的主要职责关系：

```text
context = normalize(student_profile, region_rules)
constraints = combine(context, preferences)
light_candidates = query_eligible_candidates(constraints)
ranked_candidates = assign_reference_scores(light_candidates)
page = paginate(aggregate_if_group_mode(ranked_candidates))
result = attach_details(page)
```

## 3. 缓存、统计与失效

服务端包含筛选统计缓存、推荐结果缓存及序列化结果处理等路径。缓存键结合档案和规范化筛选条件，避免把不同偏好下的结果混用；筛选更新后需要使相关统计或推荐数据失效。

这些机制按具体查询路径使用，不代表所有请求都经过同一缓存。部分候选查询通过两阶段方式直接取得结果。选择操作还需要协调当前列表、个人志愿表和可缓存状态。

## 4. Agent 工具执行协议

![Agent 协作 / Agent orchestration](../assets/agent-workflow.png)

平台以注册的工具集合连接模型与业务服务。工具负责学生档案、院校专业、政策、候选筛选及志愿表读写；模型负责理解用户问题、选择工具并组织解释。

执行路径包括：解析模型参数 → 校验对象形态和工具输入 → 检查业务权限及上下文 → 执行业务函数 → 返回结构化结果 → 生成面向用户的内容与事件。

查询和修改工具分别处理。注册元数据用于判断是否修改状态；只有满足预算与预计执行成本条件的只读工具批次，才进入并行路径，并以独立数据库会话执行。未知性质的工具按保守方式处理，而不是默认并行修改业务。

会话上下文还包含已被更新结果取代的工具读取信息。服务端通过工具输入签名及修改阶段标记区分可压缩的旧读结果，减少重复内容，同时保留工具调用与返回的配对关系。系统提示词、完整工具 schema 和内部调用预算按照平台安全策略管理。

## 5. 流式响应与任务生命周期

流式响应不只是文字逐字出现，还包含工具状态、结构化卡片、选项和业务状态。终端按事件逐步更新界面；会话与任务服务保存相关记录，并提供取消和恢复相关路径。

工具失败、传输中断、用户取消和业务完成是不同事件，不应被一个成功标记替代。平台通过追踪与事件记录组织调用过程，并根据状态、持久化进度和具体业务约束选择恢复或重新执行策略。

## 6. 志愿表解析与诊断

已有方案通过文件解析流程进入结构化记录，再关联档案条件、院校专业和方案统计，继续组织诊断内容及导出文档。解析、业务分析和成果文件分别承担不同职责。

这个结构允许方案编辑、查询与诊断复用业务数据，而不只把一份文件直接交给模型生成一段不关联平台状态的回答。

## 7. 生涯规划与报告交付

规划记录关联起始资料、会话、目标、信息采集状态、报告状态和文档。资料采集与问询推进业务，报告服务继续承接成果交付。

标准交付流程由后台文档处理推动文件可用状态：提出报告请求后，系统跟踪报告处理和资源就绪状态；文档完成后再提供列表与下载。兼容导出能力与按需生成流程分别管理，以适配不同服务场景。

产品采用“AI 问询 + 规划服务 + 统一文档交付”的协同模式，并通过审核与服务流程管理成果质量。

## 8. 多端、身份与权限

Web、小程序、iOS 和 Android 工程连接共享账号、档案、推荐和记录服务。Web 面向桌面操作与机构工作；移动端承接查询、问询、选择和分享。

身份映射、令牌和角色机制与记录归属校验共同限制业务资源的访问。机构端和个人端即使使用相同业务模型，也有不同的资源范围与操作入口。

客户端使用加载阶段、请求序号、在途刷新合并、带作用域的实体身份及局部更新等机制处理交互一致性。服务端提供最终业务状态，两者共同保持操作与显示的联系。

## 9. 技术与数据治理

平台通过模块职责、查询组织、通用映射、工具执行和状态协同形成可维护的技术体系。生产阈值、内部提示词、真实数据、私有接口、凭据和内部拓扑按照权限、安全与隐私要求管理。

各端功能按照产品版本交付；性能与模型质量则通过对应环境、数据集和验收口径持续评估。
