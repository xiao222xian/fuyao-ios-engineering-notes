# 扶摇志愿：原生 iOS 客户端工程复盘

这份原创复盘讨论一个高考志愿辅助产品中的原生 iOS 工程：怎样把已有多端产品的业务规则，落实为一致、可恢复、能够解释失败的移动端体验。

项目已结束。本文在 2026-10-14 根据归档源码和开发交接记录重新撰写，记录的是已观察到的实现、历史验证与仍待验证的问题，不提供可运行的商业项目源码、真实用户资料或内部文档。

## 先看结论

工程中的主要困难是跨页面状态一致性：同一个成绩档案、筛选条件、院校专业组和报告任务，会同时出现在多个入口。页面看起来相似，并不能保证请求参数、局部选择状态、错误恢复与实际结果相同。

这次复盘归纳出四项经验：

- 数据上下文先于 UI 还原。地区、年份、批次、科目与环境必须一致，才能比较两端结果。
- 身份与聚合状态要分开。一个专业组被选中，不能直接推导其中每个专业都被选中。
- 异步过程要有明确边界。搜索、对话流与报告文件各自有不同的完成条件。
- 验证证据必须带时间和范围。语法检查、模拟器构建、真机体验与平台发布不能合并成一个“完成”。

## 个人贡献怎样表述

保存的项目规则将主要个人职责限定在 iOS 客户端。本文把 iOS 的接口适配、状态管理、组件复用和工程验证作为个人工作复盘范围；后端推荐、AI 编排、数据治理、Web、小程序和部署作为协作系统背景介绍。

iOS 本身也有协作提交，本次没有逐项进行作者归属审计，所以不声称独立完成全部 iOS 功能，更不声称独立开发整个平台。

## 结果能支持到哪一步

归档源码中可以看到搜索请求合并、专业组状态区分、生涯规划对话和报告入口等实现。历史记录包含局部 Swift 语法检查、某些版本的模拟器构建通过，以及需要后续真机回归的清单。

此次仅审阅归档并撰写文档，没有重新构建 App、连接真实账号、测试线上服务或核验商店发布。没有可公开复核的推荐准确率、用户转化率、延迟基准或教育效果数据；本文不编造这些指标。

仓库内的示意图和符号案例均为新写的工程说明，不来自用户截图或真实学生数据。若只想了解最有代表性的技术问题，可以从[组合身份与请求合并](docs/03-algorithms-and-contracts.md)读起。
